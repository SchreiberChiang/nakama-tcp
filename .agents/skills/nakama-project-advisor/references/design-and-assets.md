# 设计、诊断与资产接入

按当前问题读取相应段落。下面是分析方法与示例，项目能力必须另查源码。

## 玩法与同步

先说明推荐体验与范围，再用少量关键问题消除影响方案的未知。可用一张小表表达“交互／权威／可见者／持续、事件、按需或本地／允许延迟／失败处理”。延迟目标可先作待测假设，不向用户保证未测网络指标。

- 赛车：油门、转向等持续控制与碰撞/圈数/终点规则分开；车轮、尾气、镜头以本机呈现为主。核对服务端如何获得赛道碰撞规则，客户端场景不能直接作为 Nakama 物理引擎。三维高度、坡面、悬挂状态需单独设计，不能硬塞二维通用时间轴。先问影响范围的碰撞竞争、人数或平台，不先要求用户选 Hz。
- 射击：移动/瞄准持续状态与开火事件分开。服务端决定合法开火、命中、伤害和胜负，本地可即时播放反馈但不能先宣告权威命中。是否需要回溯/预测取决于速度、网络和公平性要求；没有历史命中实现时明确缺口，不能靠提高快照率承诺公平。
- 隐藏信息回合制：优先事件命令、服务端回合/牌权与显式私有投影；结算也可能含秘密。客户端隐藏 UI 不是保密，公共元数据/日志/错误文本也不能泄露。分别检查两个接收者的实际序列化快照及结算，使用不同私有哨兵。低频变化仍可能随整房周期快照传输，按需/仅变化发送是设计选项，不是假定现有能力。
- 异常处理：将断线/后台/移除后的规则映射到当前生命周期。若需求要求中途加入、恢复牌局或恢复赛车原位置，而核心门禁/存储不支持，推荐可行的首版体验并标记底座扩展，不绕过身份或阶段校验。

反馈至少分为“本地已尝试／服务器接受／已消费／业务结果”，根据实际公开 API 决定能展示哪些。无回执时不要诱导重复付费/开火等动作；需要重试须先定义业务动作标识、去重范围与未知结果处理，独立评估，不顺手给现有 API 加承诺。

先区分模块业务动作 ID 与底座输入 seq：检查 payload 能否携带自有 action_id，由服务端验证并在模块投影中返回业务结果；若可行，逐动作反馈可属模块适配。只有确实需要关联底座精确输入回执，而公开 API 又不足时，才列共享接口缺口。业务 ID 本身也不产生持久去重、事务或自动重试保证。

## 先诊断再优化

在同设备、相同人数/地图/操作和固定构建上测基线。先识别指标单位与采样范围；面板某个“1M”读数不能直接称 MB/s 或有效快照流量。

| 假设 | 能区分原因的证据 | 再考虑的调整 |
|---|---|---|
| 客户端帧耗时或消息消费阻塞 | 帧间隔分布、主线程/绘制耗时、Socket 到达与 Godot 消费时间；GPU 未测就保留缺口 | 资源、脚本、渲染或批处理负载 |
| 网络延迟/抖动 | 有定义的往返探针、实际收包间隔/最长断档、有效消息字节；服务端 tick 不是 RTT | 缩减载荷、容忍陈旧、受控弱网验证 |
| 服务端超预算 | 实际运行时整 tick、input/step/投影/序列化耗时，人数与状态规模 | 规则计算、状态规模、投影成本 |
| 呈现缓冲或插值 | 到达节奏正常但时间轴欠载/保持/外推异常，采样成本与镜头对照 | 缓冲、映射、插值；衡量增加的视觉延迟 |

一次改变一个主要变量，报告分布与体验变化。已有计数器只能证明其采样范围；缺少探针时先提出最小测量，不把未执行的测量写成结论。调整频率只是可能手段。

## 第三方资产

先清点实际文件，不运行未知编辑器插件/安装脚本。材料不足时给暂定拆分和缺证据项，只问会改变授权、平台或工作量的关键问题；不得虚构检查结果。

检查 `project.godot` 与输入映射、控制器脚本、物理 tick/碰撞层/单位、Autoload、编辑器插件/GDExtension、资源引用、网络/RPC/MultiplayerPeer/Nakama 依赖、引擎版本、LICENSE/来源及转授权限制、目标平台支持。无许可文件不能推断“可商用”；缺二进制或项目时也不能断言平台兼容。

给出四部分：

1. 客户端可保留：模型、材质、动画、镜头与 UI；测大小、加载和渲染后决定优化。
2. 服务端需表达：碰撞/移动简化规则、命中/计分/胜负、选择与回合。Godot 场景/脚本不会直接在 Nakama 中运行。
3. 可复用底座：按实际合同复用 Session、房间、输入、投影、结算和模块视图。单机控制器应分离输入、规则与展示；不保留第二套 socket 作为默认捷径。
4. 需替换/改造：自带网络、全局输入争抢、平台不支持的扩展、依赖本机物理结果的逻辑、授权不明资源。说明成本和保留原资产的隔离/回退方法。

首步通常是隔离小场景或无美术规则验证，随后一个完整双人生命周期；仅当任务实际授权实现时执行。推荐真实小玩法不等于把测试 fixture 改成生产玩法。

## 风险分级回退

按实际影响采用适用的最高一级，不按改动行数分级；普通文档修订不要求协议或数据迁移流程。每步说明失败触发条件、恢复到的具体状态及恢复后怎样验证。

| 风险范围 | 回退说明的最低内容 |
|---|---|
| 低：文档、局部玩法或隔离装配，未改变共享合同与持久数据 | 恢复本次涉及的文件、配置或注册到已知基线，保护他人改动；核对引用或适用的模块行为。只有确实未改变共享状态时，才可将撤下模块、回到空底座作为完整回退。 |
| 中：共享接口、消息协议、平台装配或跨端发布 | 列明需恢复的客户端包、服务端版本、配置和合同，检查新旧客户端与服务端的兼容组合；处理仍在线的旧包、既有房间和缓存。说明切换顺序、恢复后的双端验证及不能降级的条件，不能只撤代码却让一端继续使用新协议。 |
| 高：持久数据、存档迁移、交易或不可逆外部效果 | 先确认可用恢复点、恢复方法及其验证证据，说明停写/隔离范围与可接受的数据损失窗口。旧程序能否读取新数据、已发生扣款/发货如何核对或补偿须分别说明；不能盲目恢复整库丢弃合法新写入，也不能承诺撤销已发生的外部效果。没有安全逆向路径时，停止该步并商定前向修复或补偿方案。 |

`git revert` 或恢复文件只改变源码；不会自动撤回已发布客户端、切换服务器、逆转数据库迁移或恢复协议兼容。涉及共享大改、数据恢复或外部操作时，具体方案与授权按实际范围确认；这里的回退建议本身不授予执行权限。恢复未实测就注明未验证，已知无法完整恢复的风险应在实施前明确提出。
