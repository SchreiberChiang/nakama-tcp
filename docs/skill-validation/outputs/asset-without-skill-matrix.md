建议采用“小场地、双人、简化服务端车辆运动”的方案。这份包可借用输入映射，但不足以保留一套完整车辆控制器；直接接入无法满足当前底座的权威规则。

本次仅静态读取项目及适用微信技能，未联网、修改、运行或委派。

1. **能留什么**

[car.gd](<<without-skill>/evaluation-input/vehicle-demo/car.gd>) 继承 `VehicleBody3D`，只有油门乘900、转向乘0.5和上传姿态。可保留输入意图、参数作为调校起点；实际运动依赖 Godot 物理。包中没有车辆场景、车轮、碰撞体、模型或悬挂配置，无法评价驾驶手感，也不能估算“保留百分比”。

`project.godot` 的两个输入动作均无绑定；`steer` 使用非负强度，尚未表达左右双向转向。需补键盘和触控输入、刹车及松手清零。

2. **必须替换什么**

[demo_net.gd](<<without-skill>/evaluation-input/vehicle-demo/demo_net.gd>) 使用 ENet，`any_peer` RPC直接覆盖固定路径车辆姿态，没有玩家车辆归属、轮次或输入校验。应移除该联机层及 `DemoNet` 自动加载，统一经 `Session` 发送油门、转向、刹车，不上传权威位置。微信现有 Web 路径也不能照搬原生 ENet。

服务端新增玩法模块，按底座30Hz推进运动、碰撞和计分，实现输入白名单、范围校验及 `inputExpired` 清零；保留身份、seq、round_id、sessionId和限流。包的60Hz物理不能与服务端直接视为一致。

3. **推荐的最小接入**

先做平地、边界墙、两辆车；暂缓坡道、跳跃和复杂撞车。服务端用简化平面车辆模型，客户端负责3D呈现。这样需要新增运动规则，但无需制造完整悬挂模拟。

若必须保留 `VehicleBody3D` 的真实驾驶手感，本地预测会与简化服务端模型产生误差；当前底座没有预测重演。改用服务端 Godot 物理则是额外架构工程，无法承诺“小改控制器”。

客户端用 `GameModule(Control)` 包装场地，仅在 `playing` 创建3D内容，`release()` 停止物理、清输入并释放；共享页面保持2D。现有时间轴只处理二维位置和角度，可映射平面坐标，不能直接同步完整 `Transform3D`。

4. **依赖与交付限制**

`vehicle.gdextension` 仅声明 Windows DLL路径，实际DLL也未提供；`plugin.cfg` 指向缺失的 `plugin.gd`。现有车辆脚本未显式调用扩展，建议先排除扩展和编辑器插件，不能据此保证完整包无依赖。4.6声明不等于底座4.7.2兼容证明；素材说明明确未提供许可授权，交付复用依据缺失。
