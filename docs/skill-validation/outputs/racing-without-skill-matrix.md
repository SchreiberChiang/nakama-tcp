推荐**服务端算真实车况，本机预测自己的车，其他车按快照平滑显示**。这能兼顾转向响应和防篡改，但需要新增赛车模拟与预测逻辑，底座目前还没有。

实际代码里，两端注册表为空；[Session](</<without-skill>/client/core/session.gd:93>)已有持续输入通道。[快照时间轴](</<without-skill>/client/core/snapshot_timeline.gd:2>)只支持二维位置、速度和角度，不含三维物理、预测或重演，不能直接处理腾空落地。

建议这样实现：

- **客户端只报操作**：转向、油门、刹车；通过 Session 发送。服务器计算位置、速度、碰撞、检查点和名次，保留身份、轮次、序号、限流与输入白名单校验。改客户端不能直接改比赛结果，但不能据此承诺杜绝所有外挂。
- **自己的车立即响应**：本地先用相同规则预测，收到服务器车况后校正，再重演尚未确认的操作。碰撞误差可能造成拉回，需要专门调校。现有 `applied_input_seq` 不是连续确认，不能直接拿它删除整段输入历史；须先设计持续控制与模拟步的确认关系。
- **其他车稍晚显示**：用相邻快照插值；新增高度、三维朝向、空中/接地状态。掉包时限制外推，避免预测车辆穿墙或飞远。

物理上，我建议先做**简化街机车辆模型**：简化车体碰撞、坡面接地、重力和落地响应，由服务端统一执行，本地实现对应预测。若必须有真实悬挂、翻滚和复杂堆撞，应先验证服务器物理方案；当前 TypeScript 模块并没有 Godot 车辆物理。

你不用先选频率。起步沿用：**服务器每秒算30次，操作最多每秒发30次，车况每秒发20次**。画面每秒画多少帧是另一回事；这些数字不是延迟保证。先测手感、碰撞和耗时，再决定是否细分物理步或提高频率。

第一步做一个**独立测试构建的四车灰盒试验场**：直道、弯道、斜坡、跳台、墙和检查点，先两车验证预测纠正与相撞，再四车测负载；正式底座保持空注册。验收重点是松手停止、起跳落地、相撞后双方一致、弱网纠正和伪造输入被拒。随后在微信真机与电脑同房验证；修改后补构建、SDK、双客户端和实际 PCK 审计。

目录中的车辆示例也不能直接接入：[demo_net.gd](</<without-skill>/evaluation-input/vehicle-demo/demo_net.gd:1>)另开 ENet 并接受客户端姿态，绕过现有权威边界；示例还缺授权及移动端二进制，微信兼容性未证实。

需要你决定三点：

1. 碰撞希望轻微推挤，还是能撞飞、翻车？
2. 能否接受弱网时偶尔纠正车位？目标手机大致什么档次？
3. 电脑指原生程序还是浏览器？玩家主要在哪个地区联网？

本次仅静态阅读。仓库已有跨端二维测试的历史记录，不代表四人三维赛车已通过；微信三维性能、四车弱网体验和服务器成本均未验证。
