1. **四人房间：基本支持。**已有登录、大厅、准备、开始、结算、留房再开和房主移交，容量支持到8人。新模块可设最少4人、建房容量4；若必须严格四人，还要在服务端限制该玩法容量，当前没有模块最大人数合同。洗牌、发牌、行动顺序、合法出牌和胜负都需服务端实现。

2. **私有手牌：已有合适接口，保密取决于实现。**[服务端快照](/<without-skill>/server/src/main.ts:113)按接收者调用 `snapshot`，结算另走 `projectResults`，逐人定向发送；投影失败不会退回广播原始状态。建议只下发本人手牌、其他人手牌数量和公开牌。**结束时快照与结算两条路径都必须继续过滤**，不能只在界面藏牌；牌堆顺序、随机种子也不能进入公共选项或日志。

3. **重复点击：只做了一半。**服务端检查身份、`sessionId`、`round_id`、`seq`，已有命令去重。但[每次提交](/<without-skill>/client/core/session.gd:433)都会生成新 `seq`，两次点击可能成为两个合法请求。首版应使用 `command`，增加行动编号、业务动作ID；执行时检查当前行动者、手牌归属、动作是否处理过，再一次性更新状态。按钮等待期间禁用只是体验保护。现有 `applied` 表示模块已消费，不能直接当作“出牌成功”；需业务结果。32条回执不是跨断线账本，超时不能盲目补发。

4. **切后台续原局：目前不支持。**[离房代码](/<without-skill>/server/src/main.ts:503)删除成员，进行中的房间拒绝重新加入；客户端断线清空房间状态。跨端测试的后台策略也是注销、返回后手动登录，不是恢复原局。

首版建议先做一个简单规则、纯2D、固定四人的完整闭环，再把续局作为交付必需项：服务端短时保留座位、手牌和动作记录；同账号重新认证后绑定新连接，使旧连接失效；先获取本人最新状态并核对未确认动作，再恢复操作。离线期间是否继续计时、超时如何处理必须明确。可先限定“服务进程仍存活时续局”，跨服务重启恢复另排。
