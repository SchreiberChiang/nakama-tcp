建议第一版沿用 **Godot 2D＋Nakama 权威房间＋微信现有适配路线**，先做双人小场景射击，验证移动手感和命中规则，再扩地图、武器。以下暂按 **1 对 1 对战**推荐。

1. **当前能复用什么**  
代码中两端注册表均为空；已有登录、房间、准备、结算和再来一局。[服务端](/<without-skill>/server/src/main.ts)以30Hz模拟、默认20Hz快照；Session以30Hz发送持续输入。[时间轴](/<without-skill>/client/core/snapshot_timeline.gd:2)明确只做呈现，没有移动预测、碰撞或射击回溯。测试方块不能直接视为射击基础已经完成。

2. **首版玩法范围**  
一张固定横屏场地、一种武器、左右移动、自由瞄准、按住开枪，暂不加跳跃、复杂地形和技能。电脑用A/D＋鼠标；手机左侧移动、右侧拖动瞄准并开火。两端显示相同战场范围，避免宽屏多看见敌人。房间固定两人，需要补服务端容量约束，当前通用容量是2–8人。

3. **公平命中**  
优先选有飞行时间的可见子弹：服务端计算出生位置、射速、弹道、碰撞、伤害和胜负；使用扫掠碰撞，避免30Hz下高速子弹穿过目标。同tick伤害统一结算，明确允许同归于尽，避免成员遍历顺序决定赢家。客户端只提交操作，不提交命中或位置。  
这能保证规则一致，不能消除网络优势。若你要“准星指到就瞬间命中”，应另做有上限的历史命中盒回溯，并明确掩体后受伤的取舍；现有`client_tick`只是最近快照tick，不能当开枪时间或RTT。

4. **跟手呈现**  
本人移动采用本地预测、权威校正，准星和枪口反馈立即显示；扣血、击杀等待服务器。对方使用快照插值，缓冲先沿用约117ms再实测调整，渲染目标60fps。预测需要新增明确的输入执行时间与校正合同：当前state会合并，`applied_input_seq`不是累计确认，不能据此直接重演全部输入。

5. **输入与生命周期**  
移动、瞄准、按住开火放完整state，服务端按冷却生成子弹；单次动作才用command，并以精确seq＋round核对结果。保留Session唯一网络边界、身份/轮次/限流校验。松手、失焦、打开面板立即清控制；服务端超时兜底。后台返回先沿用重新登录加入，不承诺恢复原局。玩法仅在playing创建，共享页面保持普通2D。

本次仅静态阅读，未联网、修改或运行。仓库收尾记录包含指定包的微信/iPhone与电脑证据，但不是本次验证；Android、实际射击、公网延迟、帧耗时及最新包部分触控仍未证实。后续需分平台验证双端、弱网、触控、SDK和实际PCK；微信还依赖匹配的定制引擎及HTTPS/WSS后端。
